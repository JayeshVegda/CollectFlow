# Story direction

## Start with a product promise

Choose one audience and one promise. Organize features into a meaningful journey rather than a
catalog. A useful spine is:

`tension → product principle → real-app proof → connected capabilities → consequence → brand close`

Change the spine when the product suggests a better physical or conceptual metaphor. Record at
least two rejected directions and the reason for the selected direction in `decision-matrix.md`.

## Decide the runtime from content

Budget scenes by comprehension, not by an arbitrary maximum:

- brand opening: usually 3–8 seconds;
- native credibility anchor: usually 3–7 seconds;
- dense capability: usually 6–12 seconds including a readable settle;
- lightweight proof or bridge: usually 1–5 seconds;
- closing sequence: usually 5–12 seconds.

Treat these as planning ranges, not quotas. Remove filler. Extend a feature when the audience cannot
understand its purpose before the cut. Avoid any fixed composition lasting more than 5 seconds.

## Assign one motion idea per scene

For every shot, define:

| Field | Requirement |
|---|---|
| objective | The single idea the viewer should understand |
| evidence | Claim IDs and native assets used |
| surface | Native capture required for product proof; optional constructed HTML overlay/combination |
| action | One primary motion grammar |
| emotion | The single feeling this beat should create |
| hero | The one element that owns attention |
| phases | Establish, explain, settle, handoff |
| settle frame | Frame at which parent motion stops |
| outgoing anchor | Element and geometry that carries into the next shot |
| copy | Short final on-screen language |
| sound | Cue family and exact semantic reason |

Do not repeat the same signature animation for several unrelated features. Let one animation finish
its action arc before another becomes the subject.

After the narrative and shot objectives are stable, read `motion-direction.md` and add purpose,
primary property, secondary reaction, ambient role, path, easing, exact frame phases, and rest
geometry to each shot. Do not choose animation recipes before the product meaning is clear.

## Derive a visual system

Extract and record typography, weights, spacing, radii, surface colors, semantic colors, gradients,
shadow softness, texture, icon language, device treatment, and information density. Expand the
system only when necessary for cinema-scale readability. Avoid generic neon, glass, dark-mode, or
gradient treatments that contradict the app.

Create at least one styleframe before full scene production. Use it to validate typography,
hierarchy, material, native-capture treatment, and whether the HTML layer belongs to the same
product world.
